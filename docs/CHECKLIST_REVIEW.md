## LangGraph 노드 대응

현재 캠페인: `recon → retrieve → plan → attack → probe → summarize → END`.
하위 탐색: `observe → assess → decide → act → observe`, 조건에 따라 종료.

노드 이름보다 역할과 분기 동작을 기준으로 비교했다.

| 체크리스트 노드 | 현재 대응 | 부족한 점 |
|---|---|---|
| route | 없음 | 입력 의도 분류 없음 |
| _after_route / Chat_answer | 없음 | 일반 안내와 분석 경로의 조건 분기 없음 |

| write | 보고서 생성 함수 | 정형 보고서는 있음. 초안 상태를 다음 검증 노드로 전달하는 흐름은 없음 |

## 체크박스 외에 보완할 실제 문제

### 1. 정상 경로 미완료인데 점검을 계속할 수 있음 — 우선순위 높음

`campaign.py:208`은 기준 실행의 `status == completed`만 검사한다. `agent.py:73,76,85`의 `inconclusive`·`budget_exhausted`도 실행 자체는 정상 종료되어 completed로 저장될 수 있다. `summarize()`가 `baseline_completed`를 별도로 표시하지만 후속 시나리오를 막지는 않는다.

목표 미완료를 모두 장애로 단정하면 안 되지만, 정상 경로가 확인되지 않은 점검을 완전한 검증처럼 다루어서도 안 된다. `goal_completed` 또는 작업별 기준선 조건을 gate에서 확인하고, 실패하면 진단·제한적 재계획 또는 부분 결과로 종료해야 한다.

### 2. 인증이 필요한 API 부하 측정의 신뢰성 — 우선순위 높음

`campaign.py:251`의 probe 클라이언트는 새 HTTP 클라이언트이며 브라우저의 토큰·쿠키를 전달하지 않는다. `probes.py:90`은 연결 실패·5xx·429만 오류로 세고 401/403을 오류로 세지 않는다.

따라서 인증 API가 빠르게 401을 반환하면 실제 기능을 측정하지 않았는데 낮은 지연과 낮은 오류율로 보일 수 있다. 인증 선행 조건, 기대 응답 상태/본문 검증, 인증 실패 시 부하 측정 무효 처리가 필요하다. 테스트 인증값은 보고서·Trace에서 마스킹해야 한다.

### 3. 재현 검증의 강도 — 우선순위 중간

`agent.py:129-132`는 같은 결함 코드가 다시 나타나면 confirmed로 표시한다. 외부 등록 앱의 서버 데이터는 초기화하지 않는다. 같은 엔드포인트·입력·증거의 일치, 테스트 데이터 격리·정리가 보강되어야 한다.

중복 처리 판정도 같은 변경 요청의 2xx 횟수를 근거로 한다. 실제 비즈니스 데이터가 중복 생성되었는지는 별도 조회나 검증 어댑터가 필요하다.

### 4. AI 시나리오 누락 — 우선순위 중간

기존 샘플 평가에서 규칙 기반은 11/11, AI는 9/11 결함 유형을 재현했다. AI 계획이 필요한 장애 유형을 고르게 포함하는지 확인하는 coverage validator와 누락 유형 재계획이 필요하다. 이는 새로운 앱 전체에서의 탐지율이 아니라 결함을 심은 샘플에서 버전별 1회 측정한 값이다.

### 5. 실제 Hangari 장애 원인 검증 — 제품 목표에 중요

현재 실험실은 Python·SQLite 구조 재현이며 실제 Hangari의 Spring/Hikari 측정이 아니다. 실제 Hangari에서 외부 호출 지연, DB 풀 고갈, 로그 저장의 영향까지 입증하려면 테스트 인증, Apple 의존성 Mock/Proxy, Hikari 메트릭, 요청·로그 상관 ID를 연결해야 한다. 업로드 자료만으로 해당 실행 환경이 자동 구성되지는 않는다.

## 권장 보완 순서

1. **검증 신뢰성:** 기준선 gate, 인증·기대 응답 검증, 보고서 validate/finalize. 상태를 `완료·부분 완료·판정 불가`로 구분한다.
2. **스트리밍:** 단계별 SSE 이벤트 + 프론트 수신, 이벤트 ID·재연결·중복 제거. 토큰 스트리밍은 별도 범위로 명시한다.
3. **에이전트 제어:** 프로젝트 목적에 맞춘 질의 routing, 근거 충분성 검사, 제한 횟수의 replan, 필수 장애 유형 coverage 보장.
4. **MCP 방향 보강:** 그래프가 실제로 쓰는 점검 도구, Runbook Resource, 계획 Prompt를 제공·조회하고 통합 테스트한다. 기존 MCP API 래퍼는 그대로 활용 가능하다.
5. **평가 증빙:** ADR, 실제 그래프 다이어그램, LangSmith 수신 증빙, 동일 입력 최적화 전후 반복 측정, 발표 자료. 추적 활성화 시 외부 전송되는 데이터 범위를 먼저 정한다.
6. **실행 구조:** 직렬 브라우저 실행의 이유를 문서화하고, 독립 작업만 제한 병렬화한다. Stateless가 필수이면 작업 상태·큐를 외부화하고 새 Worker가 동일 run_id를 이어 처리하도록 검증한다. DB 자체를 없앨 필요는 없다.
7. **프론트 기준:** React/Vue가 별도 필수라면 현재 일반 JS 프론트를 전환한다. 원본 PDF만으로 특정 프레임워크가 신규 과제에 반드시 요구된다고 단정하지 않는다.

- 기존 단위·통합 테스트: `103 passed in 1.76s`.
- MCP: stdio 초기화 및 도구·Prompt·Resource 목록 조회 성공.
- LangSmith: 이번 프로세스 설정에서 비활성 확인. 외부 추적 전송은 수행하지 않음.

- 문서만으로 실제 채점자의 점수를 산정하지 않음. 최종 제출 PPT는 검토 범위에서 확인되지 않음.
