# 아키텍처 결정 기록

작성일: 2026-10-21. 결정은 현재 코드의 선택과 한계를 설명하며 미구현 기능을 구현했다고 표시하지 않는다.

## ADR-001: 브라우저에서 관찰한 요청에 장애 주입

- 문제: 서비스 소스 전체를 수정하거나 배포하지 않고 실패 대응을 확인해야 한다.
- 대안: 실제 인프라 Chaos 실험, 서버 Mock 전면 교체, 브라우저 계층 주입.
- 결정: 같은 출처에서 실제 관찰한 API와 파일에 Playwright route·DevTools로 장애를 주입한다.
- 이유: 작은 로컬 프로젝트에서도 반복·격리 가능한 사용자 관점 실험을 만들 수 있다.
- 결과: 화면 대응과 HTTP 성능은 확인하지만 실제 DB 장애·서버 재시작·외부 호출의 트랜잭션 위치를 자동 입증하지 않는다. 그 범위는 별도 구조 모델 또는 실제 서비스 어댑터가 필요하다.

## ADR-002: LLM은 계획·행동, 판정은 코드와 재현

- 문제: 모델이 그럴듯한 의견만으로 결함을 확정하면 오탐과 재현 실패가 발생한다.
- 대안: LLM 단독 판정, 고정 스크립트만 사용, 역할 분리.
- 결정: 계획·다음 행동을 모델이 선택하되 허용 후보를 JSON enum으로 제한한다. 판정은 계약 코드, 확정은 새 브라우저의 같은 API·장애 조건 재현으로 수행한다.
- 결과: 증거 추적성이 좋아지지만 문구·상태 기반 규칙의 표현 의존성은 남는다. 복잡한 성공 조건과 서버 데이터 중복 여부는 서비스별 검증기가 필요하다.

## ADR-003: 누락 검증과 제한 재계획

- 문제: 초기 AI 계획은 같은 유형에 예산을 쓰면서 중요한 유형을 누락했다.
- 대안: 모델에게 무제한 재시도, 규칙만 사용, 제한 재계획과 규칙 보완.
- 결정: 관찰 후보의 유형을 검사하고 기본 1회 재계획한다. 이후에는 규칙 보완임을 표시한다.
- 결과: 예산 내 유형 보장을 강화하지만 모델 호출·지연이 늘 수 있고, 규칙 보완을 AI의 독자적 발견으로 주장할 수 없다. 예산 밖·실제 주입 실패는 부분 완료로 남긴다.

## ADR-004: 저장 스냅샷을 SSE로 전달

- 문제: 긴 에이전트 실행에서 polling보다 즉각적인 진행 확인이 필요하다.
- 대안: polling, SSE, WebSocket·메시지 브로커.
- 결정: 단방향 진행 기록에 SSE를 사용하고 SQLite 스냅샷 해시로 재연결·중복 처리를 단순화한다.
- 결과: 별도 브로커 없이 동작한다. 모든 중간 상태의 전달 보장은 없으며 큰 스냅샷의 반복 전송과 다중 사용자 확장성은 향후 과제다.

## ADR-005: 로컬 단일 프로세스와 제한 동시 실행

- 문제: 여러 브라우저·모델을 한 머신에서 동시에 실행하면 실측 간 간섭과 자원 경쟁이 커진다.
- 결정: 브라우저 점검은 세마포어로 제한하고, 부하 요청·로그·계측만 필요한 범위에서 병렬화한다. 일반 JS 프론트와 FastAPI로 빌드 의존성을 줄인다.
- 결과: 로컬 재현과 구현 설명은 단순하지만 stateless Worker·분산 부하·다중 사용자 권한 관리는 제공하지 않는다. PDF의 신규 과제에 기존 프론트 구조 전체를 복제해야 한다는 명시는 없어 현재 범위에 맞춰 선택했다.

## ADR-006: 컨텍스트 축소의 비용과 정확도를 함께 측정

- 문제: DOM·이력을 매번 그대로 전달하면 입력 토큰이 커진다. 무조건 줄이면 중요한 UI 맥락을 잃을 수 있다.
- 결정: 기본은 화면 텍스트 1,500자·최근 행동 5개이며 중복 ARIA를 제외한다. 평가용 full 조건을 따로 두고 같은 고정 관찰·목표·모델·허용 행동으로 비교한다.
- 결과: 입력 토큰·지연·허용 행동 선택 여부를 함께 기록한다. 작은 합성 폼의 결과를 긴 실제 서비스의 정확도·금전 비용 절감으로 일반화하지 않는다.
